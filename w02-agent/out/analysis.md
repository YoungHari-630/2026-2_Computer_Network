## How the problem changed from HTTP/1.1 to HTTP/3

HTTP/1.1 primarily standardizes a human-readable request/response message format and makes connections reusable. Its optional pipelining allows several outstanding requests, but responses remain ordered, so applications commonly need multiple TCP connections for concurrency. HTTP/2 moves the problem to a binary framing layer: it multiplexes streams and compresses repeated fields over one TCP connection, fixing HTTP/1.1's application-layer concurrency and header-overhead problems. However, TCP still exposes one ordered byte stream, so one lost TCP segment can stall all HTTP/2 streams.

HTTP/3 therefore changes the transport rather than adding another multiplexing layer above TCP. It maps HTTP onto QUIC's independently reliable streams, so loss affecting one stream does not stop unrelated streams, while QUIC also integrates security and supports faster connection establishment. The new deployment problem is reachability: because QUIC runs over UDP, blocked UDP can require fallback to TCP-based HTTP.
